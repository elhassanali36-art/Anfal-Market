# Render deployment runbook — Anfal Market

## Architecture decision

Keep SQLite for the initial single-store deployment. The application uses `better-sqlite3` and already supports `DB_PATH`. Deploy it as a persistent Node.js web service and mount a persistent disk at `/data`; set `DB_PATH=/data/anfal-market.db`. Do not deploy this SQLite database on an ephemeral filesystem or a typical serverless function filesystem.

The included `render.yaml` is a Blueprint starting point. It requests a Starter web service and a 1 GB persistent disk; Render persistent disks require a paid service plan. Review the current price in the Render dashboard before approving creation. The blueprint sets `autoDeploy: false` so future pushes do not silently deploy changes.

## Before deployment

1. Create a private GitHub repository for this project and upload the complete contents of this folder, preserving `server.js`, `public/`, `lib/`, `scripts/`, `test/`, and `mobile-app/`.
2. Connect that repository to Render and create a Blueprint from `render.yaml`.
3. When prompted for `ADMIN_PASSWORD`, enter a unique password of at least 14 characters. Do not commit it to Git or put it in `.env.example`.
4. `SESSION_SECRET` is generated by Render. Keep it secret and do not rotate it casually; doing so invalidates sessions.
5. Confirm the service is configured with the persistent disk mounted at `/data` before accepting real orders.
6. Deploy manually, then open `https://<render-service-host>/api/health`. Expected response: `{"ok":true,"service":"anfal-market"}`.
7. Open the admin page on the same host, sign in, replace demo products, set the store name/logo/contact details, delivery fee, payment options, and legal policies.

## SQLite retention and backup

- SQLite is acceptable for one store, one app instance, modest order volume, and a single mounted disk.
- A persistent disk is local to the service and is not a substitute for off-host backups. Run `npm run backup` from a Render Shell or one-off command, then copy the resulting file off the service and test restoration before production launch.
- The SQLite database contains products, store settings, orders, and admin sessions. Never publish it or include it in Git.
- Do not scale the service to multiple instances with separate local SQLite disks. If horizontal scaling, high availability, or multiple stores in one shared SaaS deployment become requirements, migrate transactional data to managed PostgreSQL and images to object storage before scaling.

## Release gates

Do not call the service production-ready until the health route, admin authentication, product/category CRUD, checkout, stock changes, cancellation, HTTPS cookies, disk persistence across a redeploy, and backup/restore have been tested in the deployed environment. See `EXTERNAL_RELEASE_TEST_PLAN.md`.
